## Why this note exists

The session set out to define how to use `o2-data-sources.md`: what format a data-source
requirement artefact should take, with an agent as the primary reader and a human
updating it through a UI as the secondary reader, and how that artefact would feed the
project tree, ingestion, CI/CD, transformation rules and Unity Catalog configuration.

That is not what happened. Every attempt to specify a field hit a fact nobody had written
down. Who owns the payload shape. Whether the contracts are canonical. Whether a join key
exists. Which producer a feed actually has. We stopped specifying and started
discovering, and the picture below was built from the gaps, one at a time.

This is the DKDK method working as intended. The starting artefact earned its place as a
defect surface, not as a draft. The output of the session is findings and decisions to
make, not a format.

## What we started from

`o2-data-sources.md` v1.3, 21 feeds across five branches (analytic, cra, others, perso,
project), regenerated by `o2_data_sources.sh` through the Microsoft 365 connector. Columns:
SharePoint sub-directory, filename, cadence, producer (to be confirmed), url.

Every row reads `daily`. Producers named are EPM, APP, Whoz and ADP.

## Findings

### F1. The current file is an inventory, not a requirement

`o2-data-sources.md` is generated discovery output. It records which files happen to sit
in the landing zone on the day the script ran, with dated filenames that change daily.
A requirement artefact records a commitment: owner, grain, keys, cadence, service level,
personal-data class, quality expectations. Nothing observable can produce those.

Consequence: generating tree, ingestion or Unity Catalog config from this file means
generating from an observation. The inventory's proper job is reconciliation. Continuous
Integration asserts that declared feeds actually land, and flags landed files that nobody
declared.

### F2. Three contract layers, three owners, and O2 is a third party to one of them

The chain is IS specifies the payload, middleware implements and delivers the file, O2
consumes. O2 is a party to the delivery contract only.

| Layer | Specified by | O2 is | May an agent generate config from it |
|:------|:-------------|:------|:------------------------------------|
| Delivery: path, filename pattern, cadence, format | Middleware and O2 | a party | Yes, and O2 hears about changes |
| Payload: fields, types, semantics | IS to middleware | a bystander | Only against a held, version-pinned copy of the IS requirement, and every run must still be verified |
| Canonicalisation: what the data means across sources | O2 | the owner | Yes |

Consequence: a format that does not mark authority per section invites an agent to
generate a schema from a specification O2 does not control and is not notified about.
Drift risk survives good documentation, because O2 learns about payload changes by
breaking.

### F3. Canonicalisation is deferred with no date, and the cause is a missing owner

IS does not know how to design an enterprise model, and the work is deferred until
further notice. Middleware capacity was the stated cause, but middleware only implements.
IS specifies per source application, so each payload carries one application's model, and
nobody in the chain owns a cross-application view.

That makes non-canonical the standing condition, not a temporary one. ADR-001 already
places conforming in silver, which is both the documented medallion position and the only
version of it O2 controls.

The exposure is not the deferral. It is that O2's silver definitions become the company's
de facto enterprise model, held by a data engineering team with no mandate to define
company semantics. When two business functions disagree on what a term means, the answer
lives in O2 code that nobody outside the team signed.

### F4. Data quality is segment-scoped, not feed-scoped

Corrected during the session. For `perso_workers`, the producer is APP for every payload.
ADP sits one hop upstream of APP for France only. For other countries the same fields are
keyed in by hand inside APP.

So provenance varies inside a single file, discriminated by country, and it is invisible
in the payload. A feed-level quality value would be false. Rows sourced from a system
extract and rows sourced from manual entry have different completeness, different lag and
different failure modes.

Three consequences:

- Provenance belongs in the artefact per segment, with the discriminator named, rather
  than as a note in a producer column.
- It generates something checkable. Manual-entry segments earn completeness and
  plausibility checks that extracted segments do not need.
- Use-case scoring changes. A France-only use case rates differently on data quality than
  a pan-European one, so the coverage question has to be asked on the use-case side and
  answered against the provenance map on the feed side.

### F5. Identity is the binding constraint

There is no business join key across sources. The only candidate is a UID, which is an IS
user identifier.

That is an identity-provider account, not an HR record, which produces four problems:

- Coverage fails at the population edges that matter most for talent supply and headcount.
  Contractors, joiners before provisioning and leavers after deprovisioning either have no
  UID or lose it.
- Stability is unstated. Rehires, name changes, country moves and account recycling all
  break history silently, because a row that stops matching raises nothing.
- The UID identifies a person directly, so it is personal data. A key that must be masked
  is an awkward key to build on.
- It is the third dependency on IS with no contract behind it, after payload specification
  and the canonicalisation deferral.

Consequence: joining on the natural key is not available. The standard answer is a
surrogate key in silver plus a mapping table with validity dates and a manual resolution
path for the population the UID misses. That mapping table is authoritative data created
by O2, which is a scope change. See AD-2.

> ⚠️ Unverified. No payload has been read. Whether the UID is present in the APP files,
> the Whoz files or both, and what population it covers, is unknown. Reading one sample
> per feed is a prerequisite, not a refinement.

### F6. Feeds and entities are separate artefacts

Feeds are one per landed file family and describe delivery and provenance. Entities are
one per business concept and describe meaning, keys and reconciliation. The relationship
is many to many, and the interesting decisions sit on the entity side.

Evidence in the current inventory:

- People arrive from two producers. `perso_workers` and `perso_collab_status_report` on
  the APP and Whoz side, against `others_whoz__user_report`, `__profile_report` and
  `__talent_report`. Same humans, two systems, different keys.
- Organisational structure arrives from two producers. Six `analytic_*` files from EPM
  carry business unit, department, entity, service line, site and society, while
  `project_*` files from APP carry projects and financials that must hang off those same
  dimensions. Which version of a dimension wins is an entity decision.

This also splits the citation path into `use-case-format.md`. A brief cites entities for
data availability and data quality, and cites feeds for feed-onboarding effort. One
artefact could not serve both lookups.

### F7. ADR-010 misstates the boundary

ADR-010 states the boundary as canonical SQLI data contracts, one way inbound. The
contracts are real and inbound, but they are not canonical, and will not be until further
notice (F3). Any agent reading ADR-010 today will assume conformed data arrives.

Amendment required. The deferral should be recorded as a dated assumption with a review
trigger rather than left as ambient knowledge.

### F8. The producer column in the source file is wrong for `perso_*`

Rows currently read `ADP & APP if ≠ FR`. Producer is APP for all of them. The ADP and
manual-entry detail is upstream provenance and belongs in a provenance field (F4). The fix
lands with the format rather than as a patch to the generated table.

## Verified platform mechanics

Checked against Microsoft Learn on 2026-08-04. These constrain AD-3 and should not be
re-derived.

Two claims made during the session were wrong:

- Lineage cannot reject anything. It is emitted at read and write time, so it is post-hoc
  by construction. Prevention has to come from generation or a static pre-deploy check.
- A validation table does not gate its downstream tables. Reading one from another dataset
  does not make that dataset wait. To stop downstream work, validation and downstream must
  be separate pipelines with the downstream task depending on the validation task in a job.

Mechanics that hold:

| Capability | What the documentation supports | Limits to carry |
|:-----------|:-------------------------------|:----------------|
| Expectations | Row-level SQL predicates on each record, with warn, drop or fail actions. Pass and fail counts recorded as metrics in the event log | No custom Python, no external calls, no subqueries against other tables. Aggregate thresholds are not expressible as an expectation |
| Aggregate checks | Validation-table pattern: a materialized view computing counts or a left-outer join, with `expect_or_fail` on the result | In a triggered pipeline only the offending flow fails and rolls back. Other flows keep updating |
| Rules held outside pipeline code | Databricks recommends storing expectation definitions separately from pipeline logic, and documents loading them from a Delta table or a Python module | Not supported in SQL. Python pipelines only, which matches ADR-007 |
| Resource generation from metadata | Bundles support creating resources during deployment from metadata, with a documented loop over a config list | Requires Databricks CLI 0.275.0 or above plus uv. Generates resources, not the dataset queries inside a pipeline |
| Standing measurement | Data profiling computes null and completeness fractions over time into Delta metric tables, supports custom metrics, slices and alerts | Partial region availability. Time-series and inference profiles compute over the last 30 days. Snapshot profiles cap at 4TB. Needs `MANAGE` on the object |
| Post-hoc detection | `system.access.table_lineage` holds one record per source-to-target pair, so a target reading two sources is directly queryable. `direct_access` separates direct sources from view expansion | A subset of events only, emitted when lineage can be inferred. Incomplete for pipelines using PRIVATE tables. Lost across renames. Rolling one-year window. System schemas must be enabled |

Slices in data profiling are the mechanism for the country-segmented provenance in F4.

> ⚠️ Unverified. Neither lineage page states a freshness or latency figure for the lineage
> system tables. Any alerting cadence built on them needs measuring first.

## Proposed architecture decisions

All three are `proposed`. None is approved. None may be treated as a constraint on
implementation until written as an ADR and accepted.

### AD-1 (proposed). Artefact set and authority model

Question: how many artefacts describe inbound data, and how is authority marked so an
agent knows what it may generate from.

Options:

- One flat manifest per feed, carrying delivery, payload and semantics together.
- Three artefacts: a feed contract per landed file family, a conformed entity register per
  business concept, and the generated landing registry reduced to a reconciliation input.
  Authority marked per section as agreed, external specification, or O2-owned.
- No artefact. Configuration stays hand-written and the inventory stays documentation.

Grounding: F1, F2, F4, F6, F8.

### AD-2 (proposed). Does O2 become a producer of authoritative identity data

Question: who owns cross-source identity resolution.

Options:

- O2 maintains a UID-to-surrogate mapping table with validity dates, stewardship, a
  correction workflow and audit. O2 starts producing master data.
- Push identity resolution back to IS as a prerequisite for cross-source entities.
- No cross-source person entity. Everything stays source-scoped and use cases are limited
  to single-producer questions.

Grounding: F5, and the authority axis already present in ADR-001.

This is the decision that changes what O2 is, and delivery work will force it accidentally
if it is left open.

### AD-3 (proposed). Control model for silver

Question: what actually prevents a cross-source join on an entity with no resolved key.

Options:

- Generation is mandatory. Pipelines and jobs come from the artefact through bundle
  metadata, dataset definitions and expectations come from it in the pipeline source. A
  blocked entity produces no cross-source dataset because nothing generates one.
- Silver is hand-authored, with post-hoc lineage queries raising alerts.
- Layered: generation as the control, a validation pipeline as the runtime gate through job
  task dependency, data profiling as standing measurement, lineage as the backstop that
  catches hand-written bypasses.

Grounding: the verified mechanics above. The second option cannot prevent anything, which
was established by verification rather than by preference.

## Prerequisite before any format work

Read one sample payload per feed and record, per feed, whether a UID field is present,
what population it covers, the field list, and the apparent grain.

Until that exists, every statement about grain, keys, data availability and data quality in
this project is reasoning rather than fact, and a format written now would encode imagined
fields. AD-2 and the format specification both depend on it.
