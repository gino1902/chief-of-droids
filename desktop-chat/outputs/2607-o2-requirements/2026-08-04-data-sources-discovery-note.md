## Why this note exists

The session set out to define how to use `o2-data-sources.md`: what format a data-source
requirement artefact should take, with an agent as the primary reader and a human
updating it through a UI as the secondary reader, and how that artefact would feed the
project tree, ingestion, CI/CD, transformation rules and Unity Catalog configuration.

That is not what happened. Every attempt to specify a field hit a fact nobody had written
down. Who owns the payload shape. Whether the contracts are canonical. Whether a join key
exists. Which producer a feed actually has. We stopped specifying and started
discovering, and the picture below was built from the gaps, one at a time.

This is the DKDK method working as intended. The starting artefact earned its place as a
defect surface, not as a draft. The output of the session is findings and decisions to
make, not a format.

---

## What we started from

`o2-data-sources.md` v1.3, 21 feeds across five branches (analytic, cra, others, perso,
project), regenerated by `o2_data_sources.sh` through the Microsoft 365 connector. Columns:
SharePoint sub-directory, filename, cadence, producer (to be confirmed), url.

Every row reads `daily`. Producers named are EPM, APP, Whoz and ADP.

## Findings

### F1. The current file is an inventory, not a requirement

`o2-data-sources.md` is generated discovery output. It records which files happen to sit
in the landing zone on the day the script ran, with dated filenames that change daily.
A requirement artefact records a commitment: owner, grain, keys, cadence, service level,
personal-data class, quality expectations. Nothing observable can produce those.

Consequence: generating tree, ingestion or Unity Catalog config from this file means
generating from an observation. The inventory's proper job is reconciliation. Continuous
Integration asserts that declared feeds actually land, and flags landed files that nobody
declared.

### F2. Three contract layers, three owners, and O2 is a third party to one of them

The chain is IS specifies the payload, middleware implements and delivers the file, O2
consumes. O2 is a party to the delivery contract only.

| Layer | Specified by | O2 is | May an agent generate config from it |
|:------|:-------------|:------|:------------------------------------|
| Delivery: path, filename pattern, cadence, format | Middleware and O2 | a party | Yes, and O2 hears about changes |
| Payload: fields, types, semantics | IS to middleware | a bystander | Only against a held, version-pinned copy of the IS requirement, and every run must still be verified |
| Canonicalisation: what the data means across sources | O2 | the owner | Yes |

Consequence: a format that does not mark authority per section invites an agent to
generate a schema from a specification O2 does not control and is not notified about.
Drift risk survives good documentation, because O2 learns about payload changes by
breaking.

### F3. Canonicalisation is deferred with no date, and the cause is a missing owner

IS does not know how to design an enterprise model, and the work is deferred until
further notice. Middleware capacity was the stated cause, but middleware only implements.
IS specifies per source application, so each payload carries one application's model, and
nobody in the chain owns a cross-application view.

That makes non-canonical the standing condition, not a temporary one. ADR-001 already
places conforming in silver, which is both the documented medallion position and the only
version of it O2 controls.

The exposure is not the deferral. It is that O2's silver definitions become the company's
de facto enterprise model, held by a data engineering team with no mandate to define
company semantics. When two business functions disagree on what a term means, the answer
lives in O2 code that nobody outside the team signed.

### F4. Data quality is segment-scoped, not feed-scoped

Corrected during the session. For `perso_workers`, the producer is APP for every payload.
ADP sits one hop upstream of APP for France only. For other countries the same fields are
keyed in by hand inside APP.

So provenance varies inside a single file, discriminated by country, and it is invisible
in the payload. A feed-level quality value would be false. Rows sourced from a system
extract and rows sourced from manual entry have different completeness, different lag and
different failure modes.

Three consequences:

- Provenance belongs in the artefact per segment, with the discriminator named, rather
  than as a note in a producer column.
- It generates something checkable. Manual-entry segments earn completeness and
  plausibility checks that extracted segments do not need.
- Use-case scoring changes. A France-only use case rates differently on data quality than
  a pan-European one, so the coverage question has to be asked on the use-case side and
  answered against the provenance map on the feed side.

### F5. Identity is the binding constraint, and it is already assigned elsewhere

There is no business field linking records for the same person across producers. The only
candidate is a UID, which is an IS user identifier.

That is an identity-provider account, not an HR record, which produces four problems:

- Coverage fails at the population edges that matter most for talent supply and headcount.
  Contractors, joiners before provisioning and leavers after deprovisioning either have no
  UID or lose it.
- Stability is unstated. Rehires, name changes, country moves and account recycling all
  break history silently, because a row that stops matching raises nothing.
- The UID identifies a person directly, so it is personal data. A key that must be masked
  is an awkward key to build on.
- It is the third dependency on IS with no contract behind it, after payload specification
  and the canonicalisation deferral.

The decision is not open, or not entirely. ADR-010 principle 9 already assigns id bridging
to the middleware: where a use case must relate two SaaS records by their keys and no
business field links them, the middleware carries an internal SQLI id, and the ADR
explicitly considered and rejected O2 holding that link in silver or in Lakebase. So the
agreed default is middleware-owned bridging, and O2 holding a mapping table would reverse a
decision taken on 16 July by five named people. Under `use-case-format.md`, the architecture
principles gate would fail any use case that contradicts it. See AD-2.

> ⚠️ Unverified. No payload has been read. Whether the UID is present in the APP files,
> the Whoz files or both, and what population it covers, is unknown. Reading one sample
> per feed is a prerequisite, not a refinement.

### F6. Feeds and entities are separate artefacts

Feeds are one per landed file family and describe delivery and provenance. Entities are
one per business concept and describe meaning, keys and reconciliation. The relationship
is many to many, and the interesting decisions sit on the entity side.

Evidence in the current inventory:

- People arrive from two producers. `perso_workers` and `perso_collab_status_report` on
  the APP and Whoz side, against `others_whoz__user_report`, `__profile_report` and
  `__talent_report`. Same humans, two systems, different keys.
- Organisational structure arrives from two producers. Six `analytic_*` files from EPM
  carry business unit, department, entity, service line, site and society, while
  `project_*` files from APP carry projects and financials that must hang off those same
  dimensions. Which version of a dimension wins is an entity decision.

This also splits the citation path into `use-case-format.md`. A brief cites entities for
data availability and data quality, and cites feeds for feed-onboarding effort. One
artefact could not serve both lookups.

### F7. ADR-010 states the boundary as canonical in the present tense, and it is deferred

ADR-010 principle 3 and decision 1 state that the middleware lands canonical SQLI data
contracts. Read closely, the ADR's canonical means data shaped to a SQLI-defined format
rather than a SaaS proprietary format, for tool independence. That is a narrower and
different claim from the cross-application semantic model IS has deferred.

Both senses are nonetheless deferred today, because payloads are specified per file per
source application (F2, F3). The defect in ADR-010 is therefore tense and status, not
intent: an agreed target written as current state.

Amended on 2026-08-04 as a dated amendment section, proposed and not agreed, leaving the
five-party text intact. The amendment records principle 3 as deferred, separates the two
senses of canonical, logs the open questions below, and sets the appointment of an owner
for the cross-application model as the revalidation trigger.

### F8. The producer column in the source file is wrong for `perso_*`

Rows currently read `ADP & APP if ≠ FR`. Producer is APP for all of them. The ADP and
manual-entry detail is upstream provenance and belongs in a provenance field (F4). The fix
lands with the format rather than as a patch to the generated table.

### F9. Middleware anonymisation may already destroy the only candidate join key

Surfaced by reading ADR-010 in full. Decision 6 states that personal data is filtered at
the middleware, and that encryption and anonymisation happen before landing. The only
candidate cross-producer key is an IS user identifier, which is personal data by
construction.

Nobody has checked whether the two collide. If filtering or anonymisation touches the UID,
no cross-source person entity is buildable by any route, including the middleware bridging
route in ADR-010 principle 9. That makes this the first question to answer, ahead of any
ruling on ownership.

Logged as A1 in the ADR-010 amendment.

### F10. ADR-010 and ADR-009 read as conflicting on source file removal

ADR-010 decision 2 states that the middleware removes the files once they are read.
ADR-009's standing checks require manual source cleanup because `cleanSource` is
unsupported on the SharePoint read path.

The two may describe different actors, in which case the wording needs tightening rather
than a decision. Either way it needs verifying before the SharePoint phase goes live.

Logged as A3 in the ADR-010 amendment.

### F11. The workbook pair supersedes the flat inventory, and it is a better artefact

Added 2026-08-06. `o2-data-sources.xlsx` and `domain-taxonomy.xlsx` were authored by hand and
now carry the model. Three changes matter:

- Filenames became patterns (`AAAA-MM-DD__analytic_bu.json`) rather than dated instances. That
  is the F1 correction applied: the artefact stopped recording observations and started
  declaring configuration.
- 33 rows, of which 19 active, 2 inactive and 12 planned. The 12 planned rows are subdomains
  that need a feed and have none, so the artefact is a coverage matrix that names its own gaps,
  not a list of what happens to land. That is the `Feed onboarding` backlog, already quantified.
- A taxonomy of 5 domains and 17 subdomains, with `subdomain` acting as a foreign key from
  feeds. Referential integrity is currently perfect in both directions, every referenced
  subdomain exists and every defined subdomain is used, but it holds by care rather than by
  enforcement.

Markdown views of both are generated by `xlsx_to_md.py` so the content is tracked. The
workbooks themselves are not tracked, see the open items.

### F12. `inactive` contradicts the landing zone

Added 2026-08-06. `analytic_bu` and `analytic_entity` are marked `inactive`, yet both folders
received a file on every day observed, including today. So `inactive` cannot mean "not
landing".

Either it means "not consumed by O2", in which case the label needs defining, or the middleware
is shipping feeds nobody wants, which is worth telling the middleware team. The two readings
have different actions, so the term cannot stay ambiguous.

### F13. `producer` and `source` are undefined near-duplicates

Added 2026-08-06. The workbook carries both columns. They hold identical values on most rows,
`producer` has 9 distinct values against `source`'s 6, and `Sharepoint` appears as both for
`sales-commercials`, which conflates the landing zone with a system of record.

The pair plausibly means "system that produces the file" versus "system of record", but neither
is written down. This is F2's authority question in miniature, and it has to be settled before
either column can drive configuration.

### F14. First payload read: everything is a string, and the dimension never changes

Added 2026-08-06, from `2026-08-05__analytic_site.json`, 30 records, no personal data:

- A bare JSON array with no wrapper. Fields `id`, `active`, `name`. Grain is one row per site.
- Every value is string-typed. `"id": "27"` and `"active": "1"` are strings, not a number and a
  boolean. If that holds across feeds, every typed column in silver carries a cast, and the
  VARIANT landing in ADR-009 means those casts happen at parse time rather than failing at
  ingestion.
- All 61 daily files are byte-identical in size, 2488 bytes, across two months. The dimension
  does not change yet re-lands daily. Against append-only bronze that is 30 rows times 61 days,
  so silver must reduce to a latest snapshot or every dimension join fans out. Worth asking
  whether daily is the right cadence for reference data at all (see F12 on `cadence`).
- The site dimension carries non-geographic members, `COMPTES TECHNIQUES` and `ADMIN`, alongside
  real locations, which affects anything grouping by site.

### F15. Connector reads cannot reach the feeds that matter

Added 2026-08-06. `read_resource` returns full file content, but it has no range or offset
parameter and the connector offers no download-to-disk tool, so every read passes through a
model context. Estimated per-payload sizes, from folder totals over 61 days:

| Feed group | Est. per file | Reachable by connector |
|:-----------|--------------:|:-----------------------|
| analytic, 6 feeds | 2.5 KB to 244 KB | Yes |
| perso, 3 feeds | ~3.6 MB | No |
| cra, 2 feeds | ~4.6 MB | No |
| project, 4 feeds | ~37 MB | No |
| others, 6 feeds | ~54 MB | No |

Fifteen of 21 feeds are out of reach, including every feed bearing on the identity question.
Local export plus `jq` is the only route that handles all sizes, and it also keeps values out
of any model context, which is strictly safer than the connector route.

## Verified platform mechanics

Checked against Microsoft Learn on 2026-08-04. These constrain AD-3 and should not be
re-derived.

| Capability | What the documentation supports | Limits to carry |
|:-----------|:-------------------------------|:----------------|
| Expectations | Row-level SQL predicates on each record, with warn, drop or fail actions. Pass and fail counts recorded as metrics in the event log | No custom Python, no external calls, no subqueries against other tables. Aggregate thresholds are not expressible as an expectation |
| Aggregate checks | Validation-table pattern: a materialized view computing counts or a left-outer join, with `expect_or_fail` on the result | In a triggered pipeline only the offending flow fails and rolls back. Other flows keep updating |
| Rules held outside pipeline code | Databricks recommends storing expectation definitions separately from pipeline logic, and documents loading them from a Delta table or a Python module | Not supported in SQL. Python pipelines only, which matches ADR-007 |
| Resource generation from metadata | Bundles support creating resources during deployment from metadata, with a documented loop over a config list | Requires Databricks CLI 0.275.0 or above plus uv. Generates resources, not the dataset queries inside a pipeline |
| Standing measurement | Data profiling computes null and completeness fractions over time into Delta metric tables, supports custom metrics, slices and alerts | Partial region availability. Time-series and inference profiles compute over the last 30 days. Snapshot profiles cap at 4TB. Needs `MANAGE` on the object |
| Post-hoc detection | `system.access.table_lineage` holds one record per source-to-target pair, so a target reading two sources is directly queryable. `direct_access` separates direct sources from view expansion | A subset of events only, emitted when lineage can be inferred. Incomplete for pipelines using PRIVATE tables. Lost across renames. Rolling one-year window. System schemas must be enabled |

Slices in data profiling are the mechanism for the country-segmented provenance in F4.

## Proposed architecture decisions

All three are `proposed`. None is approved. None may be treated as a constraint on
implementation until written as an ADR and accepted.

### AD-1 (proposed). Artefact set and authority model

Question: how many artefacts describe inbound data, and how is authority marked so an
agent knows what it may generate from.

Options:

- One flat manifest per feed, carrying delivery, payload and semantics together.
- Three artefacts: a feed contract per landed file family, a conformed entity register per
  business concept, and the generated landing registry reduced to a reconciliation input.
  Authority marked per section as agreed, external specification, or O2-owned.
- No artefact. Configuration stays hand-written and the inventory stays documentation.

Grounding: F1, F2, F4, F6, F8.

Sources:

- [o2-data-sources.md](o2-data-sources.md) v1.3 and `o2_data_sources.sh`, the inventory and its generator.
- [use-case-format.md](use-case-format.md) v1.1, for the citation path a brief needs.
- ADR-001 medallion layer ownership, for the bronze, silver and gold boundaries the artefacts must match.
- ADR-003 repository strategy, for the `ingestion/<producer>/`, `silver/<subject_area>/` and `use_cases/<use_case>/` layout the artefacts feed.
- This session, for the three-layer authority model. No external documentation bears on it.

### AD-2 (proposed). Does ADR-010 principle 9 extend to person identity

Question: ADR-010 principle 9 assigns id bridging to the middleware. Does that hold for
person identity across APP and Whoz, or is person identity a business entity outside its
scope.

What is established: no business field links an APP record and a Whoz record for the same
person, and the only candidate is an IS user identifier.

Principle 9 rests on two premises, and neither is settled for this case:

| Premise | Evidence state | What would settle it |
|:--------|:---------------|:---------------------|
| The case is rare | Unknown. One candidate use case needs a cross-producer person, and demand has not been counted in either direction | Count, across the use-case pipeline, how many candidate use cases must relate records from two producers where no business field links them. A brief's placement and solution sketch already reveal this |
| The bridge is a technical relationship with no business meaning | Contested judgement, not a fact. Arguable in both directions for an identity spanning payroll, staffing and delivery | A ruling by whoever owns the definition. That owner is itself an open item |

Options:

- Principle 9 holds as written. The middleware carries a SQLI person id bridging APP and
  Whoz, and O2 never resolves identity. Cost: a new middleware requirement specified by IS,
  on IS lead time, with the cross-source person entity blocked until it lands.
- Principle 9 is narrowed to technical record-to-record links, and person identity is
  excluded as a business entity. O2 owns a surrogate key plus mapping table in silver, and
  ADR-010 is superseded in part. Cost: O2 becomes a producer of authoritative identity data,
  with stewardship, a correction workflow and audit.
- Principle 9 holds and person identity is descoped. No cross-source person entity until the
  middleware provides the bridge, and use cases stay within a single producer.

Interim rule, decidable now and prejudging none of the three: no cross-source person entity
is built until A1 is answered and demand has been counted across several briefs. Until then
use cases stay within a single producer, and `key_strategy` on any person entity reads
blocked, naming both reasons. Leaving the interim rule unstated is the failure mode, because
delivery work would settle the question by accident.

Grounding: F5, F9.

Sources:

- ADR-001 medallion layer ownership, for the authoritative versus derived axis this decision turns on.
- [use-case-format.md](use-case-format.md) v1.1, for the architecture principles gate that a contradicting use case would fail.

### AD-3 (proposed). Control model for silver

Question: what actually prevents a cross-source join on an entity with no resolved key.

Options:

- Generation is mandatory. Pipelines and jobs come from the artefact through bundle
  metadata, dataset definitions and expectations come from it in the pipeline source. A
  blocked entity produces no cross-source dataset because nothing generates one.
- Silver is hand-authored, with post-hoc lineage queries raising alerts.
- Layered: generation as the control, a validation pipeline as the runtime gate through job
  task dependency, data profiling as standing measurement, lineage as the backstop that
  catches hand-written bypasses.

The second option cannot prevent anything. That was established by verification rather than
by preference.

Grounding: the verified platform mechanics above.

### AD-4 (proposed). Editing and synchronisation architecture

Added 2026-08-06. Question: where does the source of truth live, and how does a non-technical
editor change it without losing work.

Options:

- Workbook is the source of truth, YAML or markdown generated from it. Simple, but the
  authoritative artefact is then a binary with no reviewable history.
- YAML is the source of truth, workbook is a generated view, edits round-trip back through a
  merge request. The authoritative artefact is reviewable text and git provides the conflict
  resolution.
- YAML only, edited directly in the GitLab Web IDE. Simplest of all, and correct if the editor
  count stays small enough that nobody needs a grid.

Direction taken in discussion, to be confirmed in the ADR: the second option, with GitLab.
YAML in the repo is authoritative and the workbook is never committed. CI generates it as a
pipeline artifact, the editor downloads it, edits in Excel, and uploads through the GitLab web
UI, which creates a branch. CI parses the upload, regenerates the YAML, validates, and commits
into the branch. The merge is the synchronisation.

Why that shape rather than the design first sketched, which had a button in a SharePoint-hosted
workbook calling the YAML directly:

- VBA does not execute in Excel for the web, so a button in a SharePoint-hosted workbook is dead
  in exactly the browser context it was meant for.
- A button that writes to a repository needs credentials inside a workbook opened by
  non-technical users. Upload through the web UI removes that entirely.
- Bidirectional sync between two independently editable representations needs change detection,
  conflict detection and a merge policy. Routing edits through a merge request reuses machinery
  that already exists rather than inventing a protocol whose failure mode is silent overwriting.

Two guards belong in the decision, not the implementation:

- The YAML carries a schema version and CI refuses an upload whose header row does not match it.
  Otherwise an added column silently changes the contract, which is what "admin may edit the
  format" really means.
- Loading must refuse on a dirty working tree rather than warn. A warning gets clicked through.
  This is not hypothetical: TASK-084 records a read returning uncommitted content as canonical
  in this repo, which nearly destroyed 57 archive records.

Scope caution: this is universal for tabular reference and configuration data, not for
requirements generally. `use-case-format.md` is prose with nested per-driver justifications and
would be degraded by a grid. One instance is not a framework.

Condition that reopens the question: editors who cannot be given GitLab accounts. Then the
SharePoint route returns, with all of the plumbing above.

Grounding: F11, F13, and the two workbooks as they stand.

## Prerequisite before any format work

Read one sample payload per feed and record, per feed, whether a UID field is present,
what population it covers, the field list, and the apparent grain.

Until that exists, every statement about grain, keys, data availability and data quality in
this project is reasoning rather than fact, and a format written now would encode imagined
fields. AD-2 and the format specification both depend on it.

Status as of 2026-08-06: unblocked but not done. All 21 payloads dated 2026-08-05 are exported
to `desktop-chat/outputs/2608-o2-data-sources/<branch>/<leaf>/`, which is git-ignored by design
because the payloads carry personal data. Only `analytic/site` has been read (F14). The route is
`jq` over the local exports, which is deterministic, size-independent, and keeps values out of
any model context. Three commands cover it per feed: unique field paths, record count, and
non-null count for the identity field.
