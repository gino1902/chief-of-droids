## RFC 2119 keyword reference

| Keyword | Meaning |
|:--|:--|
| `MUST` / `REQUIRED` / `SHALL` | Absolute requirement — no deviation permitted |
| `MUST NOT` / `SHALL NOT` | Absolute prohibition |
| `SHOULD` / `RECOMMENDED` | Strong preference; deviation requires explicit justification |
| `SHOULD NOT` / `NOT RECOMMENDED` | Strong preference against; deviation requires justification |
| `MAY` / `OPTIONAL` | Permitted but not required |

Do not mix RFC 2119 keywords and EARS `SHALL` in the same statement.

## Modality choice rule

Modality (`MUST`/`SHALL`, `SHOULD`, `MAY`) is selected by **enforceability** and **failure semantics** of the substrate-named contract — not by surface form (numerical vs qualitative, presence of a threshold, presence of an adverb).

### Decision procedure

For every requirement, answer two questions before selecting the modal verb:

1. **Verifiable?** Can the substrate-named outcome be checked by a mechanical predicate (file read, schema match, SHA compare, count threshold, static inspection of a resolver path) at execution time or audit time?
2. **Failure consequence?** Does the substrate name a halt, reject, block, or other explicit failure path on violation — or is violation tolerated as quality degradation?

Then route by the table below.

| Verifiable | Failure consequence | Modality |
|:--|:--|:--|
| Yes | Halt / reject / block — explicit failure path named in substrate | **MUST / SHALL** |
| Yes | Degradation only — violation tolerated as quality loss | **SHOULD** |
| No (emergent property; no mechanical check) | n/a — target is aspirational | **SHOULD** + flag AC as `no verifiable condition derivable from substrate` |
| Yes | Capability is optional | **MAY** |
| Yes | Substrate silent on consequence | **SHOULD** + Warning (consequence unstated) |

**Numerical presence is irrelevant to modality.** A numeric threshold determines whether the requirement is `Bounded` (per the Quality Criteria scorecard); it does not determine binding strength. A `≥ 92%` target with no runtime enforcement is `SHOULD`. A `≤ 2000` token cap with a linter that hard-rejects on overflow is `MUST`. The number is the same shape; the contract is different.

### Worked examples

| Substrate signal | Verifiable? | Consequence | Modality | Reasoning |
|:--|:--|:--|:--|:--|
| `"≥ 92% routing reliability"` — emergent property of routing design; no runtime lever to enforce | No (emergent) | None — aspirational | **SHOULD** | The 92% is a design projection. The framework cannot detect violation at runtime; AC will resolve to `N/A — no verifiable condition derivable from substrate`. |
| `"Layer 1 token footprint MUST be minimal — Measurement: TBD"` | No (no threshold) | None named | **SHOULD** | Qualitative target with no enforcement machinery; `MUST` over-promises. |
| `"Token footprint ≤ 2000 tokens, enforced by an authoring-time linter that hard-rejects on overflow"` | Yes (linter) | Reject | **MUST** | Mechanical check (linter) + explicit halt path (reject). |
| `"Sentinel record SHALL contain seven REQUIRED fields"` | Yes (schema match) | Bind halts on missing field | **SHALL** | Schema-validatable + explicit halt; binding-strength `MUST` equivalent in EARS form. |
| `"Response time observed at ~150 ms across corpus; best-effort"` | Yes (timer) | None — best-effort | **SHOULD** | Number present but no SLO and no enforcement. |
| `"Workspace-tier-wins precedence enforced by dispatcher on every routing call"` | Yes (static inspection of resolver) | Wrong-tier resolution is the failure | **SHALL** | Mechanical resolver path + explicit precedence contract. |
| `"Project skill could be promoted to workspace when reusable across projects"` | Yes (author review at skill-creation time) | None — prompt only, no block | **SHOULD** | Author prompt is advisory; no rejection on dismissal. |
| `"Workspace skill removal SHALL be blocked while any project skill references it"` | Yes (reference scan) | Block | **SHALL** | Scan + block are both explicit in substrate. |

### Anti-patterns

- **Over-promising on emergent targets.** Writing `MUST` on a target the framework cannot mechanically verify produces a contract with no AC. If the corresponding AC resolves to `N/A — no verifiable condition derivable from substrate`, the modality must be `SHOULD` — not `MUST`. The reliability NFR with an emergent percentage is the canonical case.
- **Demoting verified halts.** Writing `SHOULD` on a contract whose violation is named as a halt, reject, or block under-binds the requirement. If the substrate names a halt path, the modality is `MUST` / `SHALL`.
- **Letting the `MUST/SHOULD` slash leak to output.** The `MUST/SHOULD` slash in entry-format templates is a placeholder. The decision procedure must collapse it to a single keyword before render. A rendered IR/NFR/SEC/OBS entry containing the literal `MUST/SHOULD` is a Phase 4 Blocking violation.

### Application to NFR-001 (reliability/correctness)

When substrate provides only an emergent reliability percentage (e.g., "92–93%" / "≥ 92%") with no enforcement machinery, NFR-001 modality is **SHOULD**. The numeric threshold lives in the `Measurement` field and the AC is rendered as `N/A — no verifiable condition derivable from substrate` (or as a measurement-corpus condition if substrate names one). Writing `MUST` is over-binding.

If substrate names an enforcement path — e.g., "framework rolls back to fail-closed mode below 92%" — the modality flips to **MUST** because the failure consequence becomes verifiable.

## IR drafting rules

Interface requirements define the contract between the component and external systems or users.

Split into two sub-sections, both always rendered:

- `IR-IN-NNN` — inbound: data and events the component receives
- `IR-OUT-NNN` — outbound: data and events the component emits

Entry format:
```
**IR-IN-NNN** — The <system> MUST [accept / expose / support / receive] <interface description>.
```

Use Event-driven EARS (`WHEN <event> the <system> SHALL <action>`) when the interface interaction is naturally event-triggered. Otherwise, use RFC 2119 statement form.

Modality choice on IR entries follows the §Modality choice rule above. Inbound `MUST accept` is typically correct because failure to accept is a halt path; outbound `SHALL emit` is typically correct because failure to emit breaks the contract.

Rules:
- Specify protocol, format, or schema where substrate provides it; omit where absent (no synthesis).
- If no interface signal in substrate, render both sub-sections as `N/A` + Warning.
- Do not describe behavior of the external system — only the component's obligations.

## NFR drafting rules

Non-functional requirements constrain quality attributes: performance, availability, scalability, reliability, capacity.

Entry format:
```
**NFR-NNN** — The <system> MUST/SHOULD <quality statement>. | Measurement: <metric> <threshold> [<window>]
```

The `MUST/SHOULD` slash above is a **placeholder**. Collapse to a single keyword per the §Modality choice rule before render. A rendered NFR containing the literal `MUST/SHOULD` is a Phase 4 Blocking violation.

Rules:
- Every NFR MUST include a Measurement field. If no quantitative signal in substrate, use `Measurement: TBD` + Warning.
- Prefer concrete thresholds over adjectives: "p99 latency < 200 ms", not "low latency".
- One quality attribute per NFR-NNN entry.
- EARS `SHALL` does not appear in NFR statements.
- An NFR with `Measurement: TBD` or `Measurement: N/A` SHALL use modality `SHOULD`, not `MUST` (per §Modality choice rule — unverifiable target).

### Mandatory NFR slots (`--type technical`)

Two NFR slots are universally rendered to guarantee a deterministic baseline shape. Additional slots are appended only when substrate provides explicit signal for the corresponding attribute — no forced N/A beyond the two universal slots.

| NFR-NNN | Attribute | Render rule |
|:--|:--|:--|
| NFR-001 | Reliability / correctness | Universal — always rendered; `N/A — substrate silent` + Warning if substrate provides no signal |
| NFR-002 | Performance | Universal — always rendered; `N/A — substrate silent` + Warning if substrate provides no signal |
| NFR-003+ | Throughput, availability, scalability, capacity, cost, footprint, determinism, or other quality attribute | Appended only when substrate provides explicit signal for the attribute. ID sequence continues from NFR-002 |

For `--type generic`, the NFR section is not rendered.

### Canonical substrate-signal → NFR-slot mapping

When substrate carries multiple quality-attribute signals, map each signal to the lowest-numbered slot whose attribute matches. This mapping is deterministic: two agents running on the same substrate produce the same NFR-NNN → signal assignment.

| Substrate signal phrase | NFR slot | Attribute |
|:--|:--|:--|
| "reliability", "correctness", "X% success rate", "routing reliability", "92%", "93%" | NFR-001 | Reliability / correctness |
| "latency", "response time", "throughput", "RPS", "QPS", "p50/p95/p99" | NFR-002 | Performance |
| "token budget", "footprint", "minimal", "context size", "per-turn cost", "memory limit" | NFR-003 | Resource / footprint |
| "deterministic", "reproducible", "same input → same output", "byte-identical" | NFR-004 | Determinism |
| "availability", "uptime", "MTBF", "MTTR", "SLO" | NFR-005 | Availability |
| "scalable", "horizontal scaling", "load capacity" | NFR-006 | Scalability |

Signals not matching any row append at the next available slot with the attribute derived from substrate phrasing. The canonical mapping is the default; users may override the slot order by declaring `<CAT>-NNN` IDs in the substrate (which Phase 2 preserves per `conventions.md` § "ID stability across iterations").

**Bounded heuristic:** if the Measurement field contains no numeric value, time unit, percentage, or volume unit, emit Warning (unbounded NFR).

## SEC drafting rules

Security requirements use RFC 2119 for access control, encryption, audit, and policy statements. Use Unwanted Behavior EARS for threat mitigations.

RFC 2119 form:
```
**SEC-NNN** — The <system> MUST/SHOULD <security statement>.
```

Unwanted Behavior EARS form:
```
**SEC-NNN** — IF <threat or violation condition> THEN the <system> SHALL <mitigation>.
```

The `MUST/SHOULD` slash above is a placeholder — collapse per §Modality choice rule before render.

### Derivability — closed enumeration

A SEC requirement is derivable ONLY when the substrate explicitly addresses one of the following categories. The trigger is substrate text, not inference from context.

| Category | Substrate must explicitly address |
|:--|:--|
| (a) Authentication | Identity assertion of a principal |
| (b) Authorization | Permission to perform an operation |
| (c) Encryption | Confidentiality of data at rest or in transit |
| (d) Audit logging | Recording of security-relevant events |
| (e) Rate limiting | Throttling against abuse |
| (f) Input validation | Defence against injection, traversal, or malformed-input attacks |

### Exclusion list — do NOT derive SEC from

- Governance, pull-request approval, or process controls → these belong in CON.
- Filesystem sandboxing implied by path conventions, when the substrate does not explicitly name the threat → CON.
- Inferred attack vectors not named by the substrate.
- Reliability or correctness guarantees that do not address a named threat → NFR.

### Empty-section rule

If the substrate addresses none of (a)–(f) explicitly, render §Security as `N/A — substrate silent on Security. Warning emitted.` and stop. Do not synthesise SEC requirements from adjacent material. Do not assign `SEC-001` to carry the N/A statement — the section heading itself records the absence (see `conventions.md` § "Substrate-gap defaults").

### Cross-linking

Cross-link to ERR entries where security violations have error handling counterparts (use `→ ERR-NNN` notation).

## OBS drafting rules

Observability requirements specify what the component MUST expose for monitoring, logging, tracing, and alerting.

Entry format:
```
**OBS-NNN** — The <system> MUST/SHOULD <observability statement>.
```

The `MUST/SHOULD` slash above is a placeholder — collapse per §Modality choice rule before render.

### Derivability — closed enumeration

An OBS requirement is derivable ONLY when the substrate explicitly addresses one of the following categories. The trigger is substrate text, not inference from context.

| Category | Substrate must explicitly address |
|:--|:--|
| (a) Metric exposure | Named metric, counter, gauge, or histogram with a quantitative semantics |
| (b) Structured log emission | Log record with retention period or destination |
| (c) Trace span emission | Distributed tracing span with parent/child relationship |
| (d) Health endpoint or probe | Liveness or readiness probe with a check predicate |
| (e) Alert threshold or escalation | Alarm condition with a trigger threshold and recipient |

### Exclusion list — do NOT derive OBS from

- Confirmation messages emitted to the user channel (e.g. anchor lines, bind acknowledgements) → these belong in IR-OUT.
- Fields persisted in a data record (timestamps, fingerprints, IDs, SHA hashes) → these belong in DR.
- Error messages surfaced to the user → these belong in ERR.
- Static configuration artifacts (version blocks, schema files) → these belong in CON.
- Internal trace records the component keeps for its own logic but does not expose → not OBS; do not surface.

### Empty-section rule

If the substrate addresses none of (a)–(e) explicitly, render §Observability as `N/A — substrate silent on Observability. Warning emitted.` and stop. Do not synthesise OBS requirements by re-categorising IR-OUT, DR, or ERR signals. Do not assign `OBS-001` to carry the N/A statement — the section heading itself records the absence (see `conventions.md` § "Substrate-gap defaults").

### Other rules

- Specify format, destination, or retention where substrate provides it; omit otherwise.
- One observability obligation per OBS-NNN entry.

## Phase 4 hygiene checks (T2)

| Check | Severity |
|:--|:--|
| Each IR, NFR, SEC, OBS entry contains at least one RFC 2119 keyword | Warning |
| Each requirement modality maps to a row in the §Modality choice rule decision table (verifiable × failure consequence) | Warning |
| `MUST` / `SHALL` paired with AC = `N/A — no verifiable condition derivable from substrate` (over-promised modality on emergent / aspirational target) | Warning |
| `SHOULD` paired with a substrate-named halt / reject / block consequence (under-bound modality) | Warning |
| Rendered output contains the literal `MUST/SHOULD` slash (placeholder not collapsed) | Blocking |
| Each NFR entry contains a Measurement field | Warning |
| NFR Measurement field contains a numeric threshold, or is explicitly `TBD` | Warning if absent and not flagged TBD |
| NFR with `Measurement: TBD` or `Measurement: N/A` uses `SHOULD`, not `MUST` | Warning if `MUST` paired with unverifiable measurement |
| EARS `SHALL` absent from pure RFC 2119 statements (IR, NFR, OBS) | Warning if present |
| IR-IN and IR-OUT sub-sections both rendered (even if `N/A`) | Warning if a sub-section is missing |
| NFR-001 (Reliability/correctness) and NFR-002 (Performance) present for `--type technical` | Warning if either is missing |
| NFR-003+ slot assignments follow the canonical mapping table | Warning if substrate signals are assigned out of canonical order without an override |
| SEC entries derive from one of categories (a)–(f) in the closed enumeration | Warning if SEC entry has no matching category |
| OBS entries derive from one of categories (a)–(e) in the closed enumeration | Warning if OBS entry has no matching category |
| SEC and OBS sections rendered as N/A SHALL NOT carry numeric IDs | Warning if `SEC-001` or `OBS-001` appears under an N/A section |
